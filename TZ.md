## Задача

Консольный агент: получает задачу на изменение небольшого проекта, сам выбирает инструменты, читает и меняет файлы, запускает тесты, решает когда закончить.

Главное — runtime агента: отделить решение модели от исполнения инструментов, ограничить опасные действия, сохранять состояние после сбоя, контролировать расход ресурсов. Язык любой.

## Тестовая задача

> Исправь расчёт итоговой стоимости заказа, чтобы тесты проходили. Тесты не меняй. Сам найди нужные файлы, внеси исправление и запусти тесты.

`workspace/order.py`:

```python
def calculate_total(prices: list[float], discount_percent: float) -> float:
    return sum(prices) - discount_percent
```

`workspace/test_order.py`:

```python
import unittest

from order import calculate_total


class OrderTest(unittest.TestCase):
    def test_discount(self) -> None:
        self.assertEqual(calculate_total([100, 50], 10), 135)

    def test_invalid_discount(self) -> None:
        for value in (-1, 101):
            with self.assertRaises(ValueError):
                calculate_total([100], value)
```

Сложность исправления order.py на оценку не влияет.

## Базовая часть (до 7 баллов)

### Блок 1. Agent loop и инструменты — 2 балла

- Цикл с tool calling: модель сама решает, какой инструмент вызвать, нужен ли следующий шаг, когда вернуть финальный ответ.
- Обязательный инструмент **Bash(command, cwd)**: запускает разрешённую команду, возвращает stdout, stderr, exit code.
- Плюс минимум один инструмент чтения и один изменения файлов (напр. `list_files`, `read_file`, `write_file`, `apply_patch`).
- Каждый инструмент передаётся модели с именем, описанием и JSON Schema аргументов. Runtime валидирует имя и аргументы до выполнения.
- Результат — сообщение `role: tool` с исходным `tool_call_id`.
- Поддержка: несколько tool calls в одном ответе, ошибки инструментов (не роняют процесс, модель получает понятный результат), завершение текстовым ответом.
- Файловые операции только внутри разрешённых директорий workspace; не выходят через `..`, абсолютный путь, симлинк.
- Bash с ограничением времени и размера вывода. Должен уметь `python3 -m unittest -v`.
- В тесте: агент использует Bash для проверки исправления, `test_order.py` не изменён.

### Блок 2. Безопасность — 2 балла

Любой tool call — недоверенный ввод. Решение принимает runtime.

| Режим | Чтение | Запись и Bash | Удаление |
|---|---|---|---|
| safe | сразу | после подтверждения | после подтверждения |
| auto | сразу | сразу, если прошло ограничения | после подтверждения |

- При запросе подтверждения агент сохраняет состояние и останавливается. Пользователь разрешает/отклоняет, тот же запуск продолжается. При отказе модель получает tool result с причиной.
- **Policy-файл**: разрешённые/запрещённые команды Bash, разрешённые/запрещённые директории (разрешённые — внутри workspace). Формат свободный, рабочий пример в проекте. Deny > allow; всё явно не разрешённое — отклоняется. Policy лежит вне workspace, изменение через инструменты запрещено.
  - Пример полей: `commands.allow`, `commands.deny`, `directories.allow`, `directories.deny`. Команды — точные строки, директории — канонические пути. Минимум по одной allow/deny команде и директории.
- Проверка безопасности отдельно от agent loop. Перед каждым исполнением заново: схема аргументов, команда целиком, аргументы, канонические пути, cwd, режим. Проверки первого слова недостаточно (pipes, подстановки, редиректы, `bash -c`). Достаточно разрешать точные простые команды и отклонять прочий Bash-синтаксис.
- Тесты: разрешённая команда, запрещённая команда, разрешённая команда в запрещённой директории, запрет поддиректории для файлового инструмента, отказ для пути через `..` или симлинк.

### Блок 3. Восстановление после сбоя — 2 балла

- Каждый запуск — `run_id`. Сохранять: историю сообщений, tool calls, результаты, решения пользователя, текущее состояние (и бюджет для 8+).
- Завершённое действие после восстановления не выполняется повторно.
- Перед действием с побочным эффектом (включая Bash) сохранять «started», после — результат. Упал между записями — вызов **неопределённый**, молча не перезапускается. Пользователь выбирает:
  - повторить (если инструмент безопасно повторяем);
  - считать шаг неуспешным и продолжить;
  - завершить запуск с ошибкой.
- Повтор того же `tool_call_id` не должен повторно менять файлы. Если имя/аргументы отличаются от сохранённых — ошибка протокола. Явный повтор неопределённого вызова — новая попытка того же tool call. Какие инструменты повторяемы — решить и обосновать.
- В тестах — управляемая точка отказа между выполнением инструмента и сохранением результата.

### Блок 4. Plan Mode — 1 балл

- До подтверждения плана — только инструменты чтения; нельзя менять/удалять файлы, вызывать Bash.
- План — структурированные данные: цель; шаги по порядку; инструменты на каждом шаге; риски, допущения, критерий готовности.
- План сохраняется с `run_id`. Ждёт явного решения: утвердить/отклонить. Исполнение только после утверждения.
- Утверждение плана не разрешает всё заранее: safe/auto правила действуют.
- Тест: до утверждения плана — ни одной операции с побочным эффектом.

## Уровень 8. Бюджеты

- Единый бюджет запуска с лимитами минимум на: число запросов к модели; число tool calls; число действий с побочным эффектом; суммарный размер результатов инструментов.
- Действует на все фазы одного `run_id` (план, исполнение, восстановление). resume / утверждение плана / повтор не обнуляют.
- Проверка лимита и списание сохраняются атомарно вместе с состоянием действия. Упал после списания — бюджет не возвращается. Действие не начинается при исчерпанном лимите.
- Пограничные случаи:
  - несколько tool calls, а остатка не хватает на всю пачку — ни один не выполняется;
  - размер результата заранее неизвестен — инструмент получает остаток, runtime обрезает вывод и помечает как неполный.
- Тесты: исчерпание каждого лимита, сохранение счётчиков после resume, сбой между списанием и сохранением результата.

## Уровень 9. Разбиение плана на задачи

- Шаги плана → задачи: id, описание, зависимости, состояние, проверяемый результат.
- Задача запускается только после успешного завершения зависимостей (последовательно достаточно).
- На исполнении каждый tool call связан с текущей задачей. Вызовы при планировании хранятся отдельно, без task_id.
- Состояние задач и результаты сохраняются с запуском. Текстового заявления модели недостаточно для завершения — runtime фиксирует подтверждение результата (вид выбрать самим).
- Детерминированный тест: ≥3 задачи, хотя бы одна зависимость. После resume завершённые задачи не перезапускаются.

## Уровень 10. Журнал изменений и безопасный откат

- Просмотр изменений `run_id` и откат по явной команде. Журнал: создание, изменение, удаление файлов. Для каждого файла: исходное состояние до первого изменения, итоговое после последнего, хеши для обнаружения посторонней правки.
- Перед каждым действием, которое может менять файлы: сверка текущего дерева с последним снимком, сохранение нового снимка (содержимое + список путей). Расхождение — стоп и конфликт. После действия — diff и хеши. Касается и Bash (можно ограничить Bash командами, не меняющими исходники/тесты). Исключения для генерируемых файлов указать явно.
- Откат восстанавливает только файлы этого запуска. Перед откатом — повторная проверка policy, путей, хешей. Если хотя бы один файл изменён извне — конфликт, ничего не перезаписывается. Журнал и откат работают после resume. Неопределённый вызов сначала разрешается по блоку 3: runtime сверяет дерево, показывает изменения, пользователь решает, относить ли их к запуску. До этого откат запрещён.
- Тесты: изменение order.py, просмотр diff, восстановление исходного файла после перезапуска, конфликт при посторонней правке.
